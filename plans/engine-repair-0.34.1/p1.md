`team launch --yes` fails 100% of dispatches on nightly `30f3b1d8`, on any machine. Captured by pointing `agents.claude.command` at a logging wrapper: the implementer subagent is spawned as `claude --print --output-format text --model sonnet -p -- "<prompt>"` — the TEXT one-shot path (`build_text_args`, `crates/maestro-core/src/agent_provider/claude/headless.rs:70`) — while the consumer `drive_provider` (`crates/maestro-core/src/orchestration/dispatch.rs:249`) only counts `StreamEvent::AssistantMessage`, which the text path never emits. Result, measured 3/3 runs: `Implementer failed: malformed parser output: provider closed stream without AssistantMessage` after ~13s, with no session log, no state record, no cost. CI stays green because `ProductionSchedulerRunner` tests use canned outputs "without touching providers" (`crates/maestro-cli/src/commands/team_launch.rs:36`).

## Reprodução

1. In any trusted project with a configured claude agent: `maestro team launch default-coder --issue <any-open-issue> --yes`
2. Wait ~15s.
   Saída observada (a real, não a esperada):

   ```
   Plan: 1 level(s) — 0 succeeded, 1 failed
     ✗ #2: Implementer failed: malformed parser output: provider closed stream without AssistantMessage
   ```

   A logging wrapper in place of the claude binary records: `[--print] [--output-format] [text] [--model] [sonnet] [-p] [--] [Implement issue #2 and return CodeChange.]`

## ADR stub

Fix at the request-builder (make dispatch build a stream request) vs at the consumer (accept text output). Recommendation: the builder — the stream path is the one with usage/cost events, and the consumer's contract is the right one. One fork, low stakes.
