The dead team engine is the standing proof that maestro needs this: `team launch` failed 100% of dispatches (text-vs-stream mismatch) while the test suite stayed green on canned fakes (`crates/maestro-cli/src/commands/team_launch.rs:36` admits "without touching providers") — nothing in the repo could even SAY "this feature is promised but unpinned". The setwave engine answers this with a guarantees registry: `wave guarantees --json` lists 122 promises, each with where it is enforced and the test that pins it, and CI keeps the list honest. A promise without a pinning test is visible as exactly that.

## Done when

- [ ] `maestro guarantees` (CLI) prints every engine promise with: the promise, where it is enforced (`file`/`symbol`), and the test that pins it — `guarantees_lists_every_promise` test passes — owner: implementer
- [ ] a `--json` flag emits the same list machine-readably — `guarantees_json_output` test passes — owner: implementer
- [ ] a repo test fails when a listed guarantee's pinning test does not exist (the registry cannot lie) — `guarantees_registry_is_pinned` test passes by scanning the test tree — owner: implementer
- [ ] the seed registry covers the engine promises this epic ships plus the 0.34.1 contract tests — `guarantees_seed_covers_engine_promises` test asserts ≥ 8 entries naming those promises — owner: reviewer

## ADR stub

Registry as data (a TOML/JSON file the test scans) vs derived from code attributes/macros. Recommendation: data file — simplest thing that can fail CI, no macro machinery. One fork.

## Out of scope

- Backfilling guarantees for the whole existing product (seed with the engine; growth is organic per PR).
- Enforcing guarantees at runtime (they pin at test time).
