In maestro the SESSION is the state machine and the issue has no lifecycle: the session record (`crates/maestro-core/src/session/types.rs:330`) is rich, but teardown empties the sessions map (measured: `maestro-state.json` holds 0 records after runs), `team_runs` persists in the type (`crates/maestro-core/src/state/types.rs:105`) yet measured 0 in real state, and multi-epic work does not fit the types — `TeamInput::IssueSet` carries exactly ONE `primary_milestone` (`crates/maestro-core/src/orchestration/scheduler.rs:33`). The setwave engine inverts this: the issue is the machine (READY → dispatched → PR → judged → merged → ledger applied), its state lives in GitHub artifacts (sub-issues, blocked_by, PR ledger, comments), the process is disposable — which is why `wave epics` can list every open epic across repos, readiest first, after any crash. Measured consequence of maestro's inversion: the TUI could not show 3 completed sessions or 4 open PRs (patch {{p4}} treats the symptom; this slice treats the cause).

## Done when

- [ ] the record derives its state from artifacts (branch, PR, labels) and reconciles on load instead of trusting a stale flag — `issue_lifecycle_reconciles_from_artifacts` test passes — owner: implementer

- [ ] team/queue inputs accept more than one milestone or epic — `team_input_accepts_multiple_milestones` test passes — owner: implementer
