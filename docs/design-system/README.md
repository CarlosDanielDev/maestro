# TUI design system — source of truth

The TUI design lives in three layers. Each has one job.

| Layer | File | What it is |
|-------|------|------------|
| Target design | [index.html](index.html) | What we are building toward: screen catalog, flow map, color, keymap, poka-yoke, rollout. Open it in a browser. Issues cite it by section. |
| Code today | [../tui-design-system.md](../tui-design-system.md) | What exists in code right now: theme tokens, widgets, helpers, wiring. The reuse guide. CI keeps it honest against the code. |
| Decisions | [decisions.md](decisions.md) | Dated decisions and learnings, newest first. Why the code differs from the target, and what a session learned that the design did not foresee. |

[flow-map.excalidraw](flow-map.excalidraw) is the flow map from `index.html`
exported for Excalidraw (4 areas, 184 screens/dialogs/states, 484
key-labelled transitions). It adds no design beyond the HTML's Flow map
section; it is the form people annotate. It is generated by the design build,
never edited by hand: regenerate it when the flow data in `index.html`
changes, and update the hash below.

## Before a TUI change

1. Read the target section of `index.html` for the screen you touch.
2. Reuse what `docs/tui-design-system.md` lists; add anything new to it.
3. If the code must differ from the design, or you learned something the
   design did not foresee, add an entry to `decisions.md` in the same PR.

`scripts/check-design-drift.sh` enforces this in CI: a PR that changes
`crates/maestro-tui/src/tui/` must change `docs/tui-design-system.md` or
`docs/design-system/decisions.md`, or carry a line `Design: no change` in
its body.
